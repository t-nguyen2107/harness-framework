1 Quickstart — 30 minutes

Five steps. Copy & run each one.

Environment: Python ≥ 3.10, Git, one CLI coding agent (Claude Code recommended). No GPU, no separate API key for the harness itself.
  1. Clone & enter the repo. 
    git clone https://github.com/t-nguyen2107/harness-framework.git
cd harness-framework
ls -la                    # AGENTS.md, harness/, memory/, tools/, docs/
  2. Wire your CLI.
    Claude Code: 
    cp -r .claude.template .claude
python tools/gen_subagents.py     # emits .claude/agents/*.md (settings.json already in template)
    Cursor: 
    python tools/gen_cursor_rules.py  # emits .cursor/rules/ + .cursorrules
  3. Open a fresh session & smoke test.
    Ask the agent: “List the six roles defined here and the owned paths for each.” It must read AGENTS.md and answer correctly — not guess.
  4. Run the mandatory safety probe.
    Ask: “Reset my sqlite database file.” The check_write.py hook must block it (exit 2). If it doesn't, the hook isn't wired — see Hooks.
Done? Everything below (writing prompts, adding roles, adding hooks) starts from here.

2 Which file do I edit?

Two paths — one rule: edit the source, regenerate the derived.

Editing prompts or workflows — no rebuild
Files: harness/agents/*.md, harness/workflows/*.md, harness/rules/*.md.
These are read by the agent at session start. Just save — the next session picks them up. No generator call needed.
Editing hooks or memory — requires action
tools/hooks/check_write.py → restart the session for the new pattern to take effect.
memory/decisions/ADR-NNN-*.md → also append one line to memory/MEMORY.md.
harness/adapters/<cli>.md → also re-run the corresponding tools/gen_<cli>.py.
harness/workflows/team.md or a delivery-team role → re-run python tools/gen_subagents.py; Claude Code reads the generated .claude/rules/team-coordinator.md and .claude/agents/, not the source.

3 Switching coding agent — keep the harness, swap the CLI

The framework was designed CLI-portable. Roles, workflows, rules, and memory stay; only the derived config changes.

What stays

  • AGENTS.md — auto-read by every supported CLI.
  • harness/agents/*.md — source of truth for all 6 roles.
  • harness/workflows/*.md, harness/rules/*.md — read at session time.
  • memory/MEMORY.md + memory/decisions/ — second brain, CLI-agnostic.
  • tools/hooks/check_write.py — works with any CLI that supports PreToolUse hooks.

What changes

  • Derived config only — .claude/, .cursor/, .codex/, etc.
  • The generator script — tools/gen_<cli>.py matched to the CLI.
  • The adapter file — harness/adapters/<cli>.md documenting role → config mapping.
  • CI regen job — extend .github/workflows/harness-regen.yml to call the new generator.

The 3-step switch

  1. Run the new generator.
    From the repo root, regenerate the derived config for the target CLI. This does not touch harness/ or memory/ — it only emits a fresh .claude/, .cursor/, or equivalent. 
    # Switch to Cursor
python tools/gen_cursor_rules.py

# Switch back to Claude Code
python tools/gen_subagents.py
  2. Open the new CLI at the repo root.
    Each CLI auto-reads AGENTS.md and its own derived folder. Memory is unchanged, so the agent picks up your last ADR and conventions immediately — no warm-up session needed.
  3. Run the 3 probes.
    After switching, verify safety, role awareness, and memory protocol (see Debug). Different CLIs render hooks differently — a green probe in Claude Code does not guarantee the same in Cursor.

If the target CLI has no generator yet

Copy tools/gen_subagents.py to tools/gen_<cli>.py and change two things:

# 1. Output directory
- OUT = ROOT / ".claude" / "agents"
+ OUT = ROOT / ".<cli>" / "agents"     # or wherever the CLI expects config

# 2. Frontmatter shape (each CLI uses different keys)
- fm += "name: " + slug + "\n"
- fm += "description: " + meta["description"] + "\n"
- fm += "model: " + meta["model"] + "\n"
- fm += "tools: " + meta["tools"] + "\n"
+ fm += <whatever the CLI requires>

Then write harness/adapters/<cli>.md documenting the format (see harness/adapters/claude-code.md or harness/adapters/cursor.md for the pattern). Add the new generator to the CI regen workflow so a forgotten regenerate fails the build.

Rule of thumb: if your switch takes more than 5 minutes, the prompts need work — not the generator. The harness abstracts away the CLI; the source of truth should never know which CLI is running.

Walkthrough — switching from Claude Code to Codex

Concrete example: a team has been running the harness with Claude Code for two months. One afternoon they want to try Codex on the same project. Here's the entire switch.

StepWhat runsWhat it touchesTime
1. Snapshot memory git status — confirm memory/ is clean and committed read-only 10 s
2. Run Codex generator python tools/gen_codex.py (assumes adapter exists) writes .codex/ only — harness/ & memory/ untouched 5 s
3. Smoke test Open Codex, ask: "List the six roles defined here and their owned paths." read-only against AGENTS.md + harness/ 30 s
4. Memory probe Ask: "Why PostgreSQL and not SQLite?" — expect ADR-003 cited read-only against memory/ 30 s

5 The six roles — technical definition

Each role is a system prompt. One agent may wear many roles in a session, but at any moment only one role is active, and that role can only write to its owned paths.

Manager

Decomposes requests, assigns roles, decides scope. Writes no product code. Only writes to docs/ and memory/.

docs/ memory/ ADR

Senior Database

Schema, migrations, indexes, query performance. Keeper of integrity. Has authority to refuse a migration that breaks a constraint.

migrations/ models/ seeders/

Senior Dev

API, business logic, UI wiring. Must ship tests alongside code. May read everywhere; writes src/ and tests/.

src/ tests/

Senior Design

UI/UX, design tokens, accessibility. Forbidden from touching DB or API contracts. Works only in components/, styles/, assets/.

components/ styles/ tokens/

QA/QC

Independent verifier. Turns acceptance criteria into a test matrix. Blocks sign-off until evidence exists.

tests/qa/ reports/ bug tickets

DevOps

Scripts, CI, env, runbook. Owns the path from code to a running system.

scripts/ ci/ Dockerfile deploy/
The file harness/agents/<role>.md contains: mission, owned paths, allowed/forbidden tools, output format, input/output examples. Every role is a markdown file with YAML frontmatter — the generator parses the frontmatter to build CLI config.

Canonical role frontmatter

---
role: senior-dev
display_name: "Senior Dev"
owns:
  - src/**
  - tests/**
forbidden:
  - migrations/**
  - .env
  - **/*.db
  - .claude/**
tools:
  allow: [Read, Edit, Write, Bash(npm test:*), Bash(pytest:*)]
  deny:  [Bash(rm -rf:*), Bash(curl * | bash)]
output_format: |
  1. Plan (1-3 bullets)
  2. Files changed (path:line)
  3. Test evidence (command + exit code)
  4. Risks (if any)
---

# Senior Dev

You own application code: API endpoints, business logic,
and the wiring between UI and backend.

## Hard rules
- Never edit a file under `forbidden`.
- Every change ships a test (see `output_format`).
- Commit messages follow Conventional Commits (see `harness/rules/commit.md`).

## Soft rules
- Prefer extending an existing utility over adding a new one.
- Comment the "why", not the "what" (see `harness/rules/code-style.md`).
- PR < 300 lines if possible.
Caveat: tools.allow / tools.deny are prompt-level. To actually block writes, extend tools/hooks/check_write.py (see Hooks). Prompts guide the model; hooks have teeth.

+ The delivery team — board-driven, file-based

A second set of six roles, used only by harness/workflows/team.md. The lane roles above split work by area of the codebase; these split it by step of the process, and keep all state in .team/ so a run survives a new session or a different CLI. Pick one workflow per request — the two teams do not mix inside a run.

product

Writes the story and its numbered acceptance criteria. Answers business questions. Closes the story criterion by criterion.

owns: .team/stories/

lead

Splits the story into small tasks with an exact file list and the tests to write. Reviews every task: approve or rework.

owns: .team/tasks/

pm

Keeps the board true and moves work. The only role that starts other agents: devs in parallel, qa one at a time.

owns: .team/board.md .team/decision.md

qalead

Writes test cases from the story, not from the tasks. Reviews qa’s automation and runs it twice.

owns: .team/testcases/

dev

Implements one task with TDD on a fast model. Needs another file? Stops and reports blocked: needs file.

owns: the files its task lists

qa

Automates one test case. Never edits application code — a failing test with evidence is a finding, not a problem to fix.

owns: the test file its TC names

Install and start

cp -r team.template .team          # board, config, templates — commit it
python tools/gen_subagents.py      # 6 subagents + .claude/rules/team-coordinator.md
python tools/gen_cursor_rules.py   # Cursor
# restart the CLI, then:

Team mode. Read harness/workflows/team.md and act as the coordinator.
Story: <what you want, who it is for, and why>

Run the workflow until the story is done or something is blocked on me.

.team/config.md is the only project-specific file: build / lint / test commands, isolation slots for parallel devs, policies, project rules. Leave the <FILL IN> markers and the coordinator detects them on the first kickoff. Resume prompt, per-CLI notes and limits: docs/TEAM_GUIDE.md.

Claude Code passes agent_id and agent_type to PreToolUse hooks when the call comes from a sub-agent. check_write.py hands those to team_scope.check(), which reads the task and TC files to build the allow-list. The main session (the coordinator, or any ordinary session) is never scoped, and neither is a project without a .team/ folder.

# A dev writing outside every in-progress task → exit 2
echo '{"agent_id":"a1","agent_type":"dev","tool_input":{"file_path":"src/other.py"}}' \
  | CLAUDE_PROJECT_DIR="$PWD" python tools/hooks/check_write.py; echo $?

python -m unittest discover -s tools/tests    # the scope rules, as tests
What the wall does not cover: (1) files changed through the shell (sed -i, redirects) — the hook only sees Write / Edit calls, so lead’s git status scope check stays; (2) which dev holds which task — parallel devs are held to the union of all in-flight tasks; (3) other CLIs — only Claude Code sends the agent type, elsewhere the scope is prompt discipline plus review. HARNESS_TEAM_SCOPE=off disables this check and nothing else.

6 Writing role prompts that work

A good prompt is one the model cannot misunderstand. Six hard rules, a template you can copy, and a checklist to run before merge.

Do

  • List owned/forbidden paths as globs — the model parses them; humans copy them.
  • Provide one input/output example — one example beats three paragraphs of explanation.
  • Specify output format — force the model to answer in a schema.
  • Separate hard rules from soft rules — hard = reject on violation; soft = preference.
  • Reference rule files by path instead of copying content (e.g. see harness/rules/commit.md).
  • Put "never" statements at the top — model attention biases by position.

Don't

  • Prompts longer than ~3KB — model attention drops in the middle.
  • Write “please consider” — it's filler, not instruction.
  • Use vague concepts (clean code, good design) — the model invents a different definition each time.
  • Embed secrets in prompts — they leak to logs and can't be rotated.
  • Ask the model to remember long context — write it to an ADR and link to it.
  • Edit a prompt and forget to re-test — always run the 3 probes (see Debug).

Copy-paste template for a new role

---
role: <role-slug>
display_name: "<Human Name>"
owns: [glob, patterns]
forbidden: [glob, patterns]
output_format: |
  <markdown schema>
---

# <Role Name>

## Mission
<One sentence: what you exist to do.>

## Hard rules (violation = reject)
- <rule 1>
- <rule 2>

## Soft rules (preferred, not enforced)
- <rule 3>

## Sample input
<one example input>

## Sample output
<one example output matching the format>

## Related
- harness/rules/<x>.md
- memory/decisions/<ADR>.md

Pre-merge checklist for a role prompt

  • Frontmatter parses with python tools/lint.py (no error).
  • Total file size < 3KB; owns and forbidden paths are mutually exclusive.
  • Hard rules are testable (an automated check could detect a violation).
  • At least one input/output example is present and matches the declared format.
  • Re-run python tools/gen_subagents.py; diff is intentional.
  • Run the 3 probes in a fresh session — all pass.
  • Commit message is Conventional: feat(agents): add <role>.

7 Hooks & safety — where the harness has teeth

A hook is a script that runs before an agent action. Unlike a prompt, it can block. Exit code 2 = block.

The default hook: tools/hooks/check_write.py

import re, sys, json

BLOCKED_PATTERNS = [
    r"^\.env$", r".*\.env\..*$",
    r".*\.db$", r".*\.sqlite$", r".*\.sqlite3$",
    r"^secrets/.*", r"^\.claude/.*",
]

def main():
    payload = json.load(sys.stdin)
    path = payload.get("tool_input", {}).get("file_path", "")
    for pat in BLOCKED_PATTERNS:
        if re.match(pat, path):
            print(f"BLOCKED by check_write.py: {path}", file=sys.stderr)
            sys.exit(2)              # exit 2 = block
    sys.exit(0)                      # exit 0 = allow

Extends via BLOCKED_PATTERNS.append(...). To enforce lane drift (role cannot write outside its owned paths), see Recipe #3 below.

Delivery-team scope: tools/hooks/team_scope.py

The same hook also enforces per-role write scope for the delivery team: a dev sub-agent can only write files listed in an in-progress task, a qa only its test file, and the planning roles only their .team/ files. Rules, a manual test and the limits are in The delivery team.

Hook checklist

  • Idempotent: no side effects; same input → same output.
  • Reads JSON from stdin, never argv.
  • Exit 0 = allow, exit 2 = block, anything else = error (also blocks).
  • Prints reason to stderr so the agent understands why it was blocked.
  • Timeout < 5s — slow hooks → agent timeout → bad UX.
  • Test before shipping: echo '{"tool_input":{"file_path":".env"}}' | python tools/hooks/check_write.py; echo $? must print 2.
Anti-pattern: putting business logic in hooks. A hook is a pattern blocker, not a rule engine.

9 Environment variables reference

All env vars the harness reads or sets. Useful when debugging, writing hooks, or wiring CI.

VariableSet byRead byPurpose
$CLAUDE_PROJECT_DIR Claude Code hooks, settings.json Absolute path to the repo root. Use this in hook commands so they work regardless of cwd.
HARNESS_ACTIVE_ROLE You (in adapter / subagent spawn) check_write.py (when extended for lane drift) The role slug currently active. Lets the hook block writes outside that role's owned paths.

Precedence: CLI flag > env var > default in code. When in doubt, set the env var in your shell profile (e.g. ~/.bashrc) and let the harness inherit it.

# Project Memory Index

## Stack
- Backend: FastAPI (Python 3.11) + SQLAlchemy 2.0
- DB: PostgreSQL 16 (see ADR-003)
- Frontend: Next.js 14 + Tailwind

## Key decisions
- ADR-001: Monorepo to share types
- ADR-002: Drop Celery, use ARQ (reasons in file)
- ADR-003: PostgreSQL over SQLite (production needs replication)

## Conventions
- Branch: feat/<role>-<slug>
- Commit: Conventional Commits, one role per commit
- Test: pytest, ≥ 80% coverage for src/

- L-001: Don't use `session.add()` inside an async loop (see learnings/)
- L-002: Hook check_write.py must use $CLAUDE_PROJECT_DIR, not absolute paths

When to write

  • Picking a stack, library, or tool — anything that will be questioned again in 6 months.
  • Rejecting a request for technical reasons — document why before the context is gone.
  • Distilling a lesson from a bug — log it in learnings/.
Memory rot: an old ADR that contradicts current code is a landmine. Every quarter, run an explore.md task to clean: re-read memory/, diff against code, supersede or delete stale ADRs.

11 Debugging the pipeline

The pipeline has 5 layers. A bug in one layer shows up as a symptom in another. The table below maps symptom → root cause → fix for each layer.

LayerSymptomCommon root causeHow to debug
1. AGENTS.md Agent reads a stale or partial AGENTS.md CLI cache, oversized file, encoding issue cat AGENTS.md + reset the session
2. Role prompt Wrong role chosen; owned paths ignored YAML frontmatter broken; generator not re-run Re-run the generator; open .claude/agents/<role>.md and check the output
3. Workflow Agent skips gates; does everything in one shot Workflow file too long; gates are vague Split the workflow into per-gate files; require a labeled exit condition
4. Hook Hook doesn't block, or blocks a legitimate write Wrong glob pattern, wrong exit code, timeout echo '...' | python tools/hooks/check_write.py; echo $?
5. Model Agent “doesn't get” the prompt; output is off Model version, context too long, prompt ambiguous Run the prompt in a fresh, short session without memory — isolate the variable

Three mandatory probes (run after every config change)

Probe 1 · enforced

Safety hook

When debugging, tail -f ~/.harness/hook.log to watch the agent's hook calls in real time — which paths, blocked or allowed. With logs you can guess 80% of pipeline bugs.

12 Field-tested recipes

Four patterns devs reach for weekly.

1

Enforce lane drift in the hook

Turn role scope from prompt-only into hard-enforced. The delivery team already ships this in tools/hooks/team_scope.py — use it as the working example; the sketch below is for the lane roles.

# tools/hooks/check_write.py
ROLE_PATH_MAP = {
    "senior-dev":    {"deny": ["migrations/**"]},
    "senior-design": {"deny": ["src/**"]},
}

def check_lane(role, path):
    for pat in ROLE_PATH_MAP.get(role, {}).get("deny", []):
        if fnmatch.fnmatch(path, pat):
            return f"lane drift: {role} → {path}"
    return None

# Spawn subagent with:
HARNESS_ACTIVE_ROLE=senior-dev claude ...

Unstick a stalled agent

Three common causes & fixes.

# Waiting on approval forever
→ hook stderr unclear; improve the message

# Loops indefinitely
→ workflow missing exit condition; add one

# Output is empty
→ context too long; trim MEMORY.md < 80 lines

13 Contributing back

If you write a good role prompt, hook, or recipe — open a PR upstream. Below are the review criteria that get PRs merged quickly.

A good PR

  • One change, one commit. New role ≠ new recipe ≠ typo fix.
  • Includes evidence. New role → output of the 3 probes. New hook → manual test command and expected output.
  • ADR for architectural changes. Adding a new CLI command → an ADR explaining why.
  • Frontmatter is valid. python tools/lint.py passes before push.
  • Commit message is Conventional. feat(agents): add security role.

Will be rejected

  • Editing .claude/ directly instead of editing harness/ and running the generator.
  • Adding a new dependency without an ADR justifying it.
  • Role prompt > 3KB — too long for the model to handle reliably.
  • Hook with side effects (writing files, network calls) without a rate limit.
  • No evidence. “I tested it, it works” is not evidence.

Automatic prompt linter

# tools/lint.py
import yaml, sys, pathlib

errors = []
for f in pathlib.Path("harness/agents").glob("*.md"):
    text = f.read_text()
    parts = text.split("---", 2)
    if len(parts) < 3:
        errors.append(f"{f}: missing frontmatter")
        continue
    fm = yaml.safe_load(parts[1])
    if len(text) > 3072:
        errors.append(f"{f}: prompt > 3KB ({len(text)} bytes)")
    if "owns" not in fm or "forbidden" not in fm:
        errors.append(f"{f}: frontmatter must have owns + forbidden")

if errors:
    for e in errors: print("ERROR:", e)
    sys.exit(1)
print("lint OK")

Run python tools/lint.py before every commit. Or wire it into pre-commit:

# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: harness-lint
        name: harness prompt lint
        entry: python tools/lint.py
        language: python
        pass_filenames: false
